# 智程 · AI 跑步教练当前版本 PRD

> 文档版本：当前实现基线 1.0 ｜ 面向：C 端 Web Demo / 后续 uni-app 移动端迁移

## 0. 文档说明

本文档是当前产品实现的主 PRD。它描述用户问题、产品目标、页面流程、AI 计划生成、训练执行、训练反馈、动态调整、数据模型、接口和验收口径。AI 接口的字段级契约见同目录下的《AI训练计划生成与动态调整接口契约》；动态调整机制见《AI动态调整计划机制说明书》。

## 1. 产品范围

智程面向普通跑者提供 10 公里、8 周训练计划。用户完成建档后，系统把跑者档案、训练目标和训练模板交给 AI，由 AI 生成完整的周计划和每日课次。

当前产品闭环为：

```text
登录 / 注册 → AI 建档 → 档案确认 → AI 生成计划 → 用户确认
→ 今日训练 → 浏览器 GPS 记录 → 训练反馈 → AI 评估后续计划
→ 用户采纳调整 → 继续执行新计划
```

### 1.1 用户问题

普通跑者通常知道自己想跑得更快，却难以把目标转化为可执行的训练安排。固定模板无法充分理解用户的训练基础、可用时间、伤病情况和实际完成表现。智程让用户先完成结构化建档，再由 AI 生成每天可执行的训练内容，并根据真实训练结果持续调整后续安排。

### 1.2 产品价值

| 用户阶段 | 用户需要 | 产品提供 |
| --- | --- | --- |
| 建档前 | 不知道需要提供哪些信息 | 分步骤 AI 建档和风险筛查 |
| 生成计划 | 担心计划过难或不适合自己 | AI 结合档案和训练模板生成 8 周计划 |
| 训练当天 | 不清楚热身、主体和拉伸怎么做 | 具体动作、距离、时长和配速 |
| 训练结束 | 不知道完成情况是否正常 | GPS 客观数据与用户反馈结合分析 |
| 连续训练 | 计划与实际能力逐渐偏离 | AI 评估并给出后续计划调整 |

### 1.3 版本边界

当前版本聚焦普通跑者的 10 公里、8 周训练目标，支持浏览器 GPS 和 MySQL 服务端闭环。移动端通过 uni-app 迁移时复用页面业务结构、接口和 GPS 服务适配层。历史列表、数据趋势、社交、天气、手表同步和完整动作视频不属于当前交付范围。

## 2. 页面范围

用户可见的核心页面：

1. 登录 / 注册
2. AI 建档
3. 档案确认
4. AI 训练计划确认
5. 训练计划
6. 今日训练
7. GPS 实时训练
8. 训练总结
9. 训练反馈
10. 我的

产品当前不提供历史训练列表、数据趋势和独立的计划调整页面。历史训练数据仍保存在服务端，用于 AI 评估后续计划。

### 2.1 页面与路由

| 编号 | 页面 | 路由 | 主要任务 |
| --- | --- | --- | --- |
| 01 | 登录 / 注册 | `/login` | 建立账号和登录态 |
| 02 | AI 建档 | `/profile` | 采集档案、目标和风险信息 |
| 03 | 档案确认 | `/profile/confirm` | 检查并确认跑者档案 |
| 04 | AI 训练计划确认 | `/profile/plan-confirm` | 查看 AI 生成结果并选择目标成绩方案 |
| 05 | 训练计划 | `/plan` | 查看 8 周计划、阶段和当前待练课次 |
| 06 | 今日训练 | `/run/prep` | 查看课次结构、热身、拉伸并开始跑步 |
| 07 | GPS 实时训练 | `/run/live` | 倒计时、定位、轨迹、距离、用时和配速 |
| 08 | 训练总结 | `/summary` | 查看本次训练数据和 AI 判断 |
| 09 | 训练反馈 | `/feedback` | 填写 RPE、疲劳、不适和备注 |
| 10 | 我的 | `/me` | 修改头像、昵称、性别和隐私设置 |

### 2.2 页面交互原则

- 页面显示的计划内容以服务端当前计划为准；
- 进入计划页时默认定位到用户当前待练课次所在周；
- 训练动作由 AI 选择动作 ID，前端展示后端补齐的名称、时长和说明；
- 用户完成主体跑步后才能记录当日训练；
- 训练反馈提交后回到计划页，用户看到新的待练内容；
- 只有用户确认采纳调整后，调整后的计划版本才成为当前执行版本。

## 3. AI 计划生成

AI 接收以下信息：

- 跑者档案、训练基础、目标成绩和可训练时间；
- 训练类型、训练阶段和训练模板；
- 伤病与风险筛查结果；
- 可用训练场地和器材。

AI 输出 8 周计划，每节课包含：

- 训练类型、距离、时长和配速区间；
- 训练说明与主体结构；
- 练前动态激活动作；
- 主体跑步训练；
- 练后静态拉伸动作；
- 个性化适配说明。

热身和拉伸动作只能使用动作库中的动作 ID。后端在保存前校验动作存在性、训练类型适配、单次时长、距离、阶段衔接和安全边界。

### 3.1 生成输入

| 输入分组 | 具体字段 |
| --- | --- |
| 基本档案 | 性别、出生年份、身高、体重 |
| 训练基础 | 跑步年限、每周跑步次数、近 3 个月周跑量、最近最长连续跑 |
| 成绩能力 | 5 公里 / 10 公里成绩、舒服慢跑配速 |
| 训练目标 | 目标距离、目标成绩、目标配速、训练周期 |
| 训练条件 | 每周可训练天数、单次最大时长、主要场地、可用器材 |
| 安全信息 | 近期伤病、不适部位、风险筛查答案和风险等级 |
| 模板上下文 | 阶段顺序、回撤周、周期末减量、训练类型候选和周跑量参考 |

### 3.2 AI 生成输出

计划整体包含：

```json
{
  "targetDistance": "10K",
  "goalPace": "6分23秒/公里",
  "goalTotalSec": 3820,
  "currentWeek": 1,
  "totalWeeks": 8,
  "weeks": [],
  "zoneDistribution": {},
  "adaptationSummary": []
}
```

每周包含阶段、训练重点、目标跑量、回撤 / 减量标记和训练课次。每节跑步课次至少包含：

```json
{
  "id": "w1s1",
  "type": "easy",
  "title": "轻松有氧跑",
  "distanceKm": 4.6,
  "durationMin": 30,
  "intensity": { "paceLow": 383, "paceHigh": 404, "rpe": [2, 4] },
  "description": "保持呼吸稳定，完成计划距离。",
  "structure": { "pattern": "主体跑步训练" },
  "preRunWarmup": {
    "title": "练前动态激活",
    "duration": 5,
    "exercises": ["wu_ankle", "wu_swing"]
  },
  "mainRun": {
    "type": "easy",
    "distanceKm": 4.6,
    "durationMin": 30,
    "pace": "6分23秒–6分44秒/公里"
  },
  "postRunStretch": {
    "title": "练后静态拉伸",
    "duration": 5,
    "exercises": ["cd_calf", "cd_hamstring"]
  },
  "adaptationNote": "结合近期周跑量和可用训练时间安排。"
}
```

### 3.3 生成过程

```text
跑者档案 + 训练模板
        ↓
AI 生成 8 周训练骨架
        ↓
AI 结合每周阶段生成具体课次和动作 ID
        ↓
后端解析与安全校验
        ↓
保存 training_plan / plan_week / plan_session
        ↓
前端展示具体训练内容
```

AI 不自由编造动作名称。动作库提供动作 ID、名称、适用训练类型、默认时长、动作说明和风险标记。模型只提交 ID，后端根据 ID 补齐展示内容并拒绝不存在或不适配的动作。

### 3.4 成绩建议

当用户当前最好成绩与计划目标成绩存在明显差距时，AI 计划确认页展示建议成绩。用户可以选择“采用建议成绩并生成计划”，也可以选择“保留当前目标继续”。两种选择都会把最终采用的目标成绩传给计划生成接口，后续计划必须使用该目标作为生成依据。

## 4. 训练计划结构

### 4.1 周计划

当前周期为 8 周。每周由训练阶段、训练重点、周目标跑量、强度分布和具体课次组成。页面展示 W1–W8 的阶段进阶全貌，用户选择某周后查看该周课次。

阶段名称由 AI 根据计划生成结果返回，页面按照返回的阶段内容展示适应 / 基础、回撤周、专项提升等信息。产品不额外设置“比赛周”页面概念；周期末减量由 AI 返回的阶段标记和训练内容体现。

### 4.2 课次类型

| 类型 | 页面名称 | 典型用途 |
| --- | --- | --- |
| `easy` | 轻松有氧跑 | 建立有氧基础和训练连续性 |
| `recovery` | 恢复跑 | 低负荷恢复 |
| `long` | 长距离慢跑 | 提升持续跑能力 |
| `tempo` | 节奏跑 | 提升受控持续速度 |
| `interval` | 间歇跑 | 提升速度储备和速度耐力 |
| `race` | 目标配速跑 | 熟悉目标配速 |
| `strength` | 跑者专项力量 | 提升髋、核心和下肢稳定性 |

### 4.3 强度展示

计划页展示全周期强度分布和各周强度变化线。训练页展示本课次目标距离、时长、配速区间、RPE 区间和训练结构。训练说明使用距离、时长、配速和呼吸稳定等可执行信息，不使用“跑步时能否说话”作为评判标准。

## 5. AI 动态调整

用户提交训练反馈后，后端把本次训练的 GPS 数据、计划目标、反馈信息、身体不适、近期训练状态和历史调整记录交给 AI。

AI 负责理解训练状态，判断是否需要调整，并生成后续课次的具体变更、原因和复核条件。调整结果只影响尚未完成的课程，已完成课程保持原记录。用户采纳后，服务端生成新的计划版本并写回数据库。

调整内容可以包括训练类型、距离、时长、配速、动作内容和训练说明。后端负责校验 AI 输出，确保动作来自动作库、数据可执行、调整范围安全，并保留调整前后版本。

### 5.1 调整判断输入

| 输入 | 用途 |
| --- | --- |
| 计划课次 | 判断实际完成与目标之间的差异 |
| GPS 数据 | 获取实际距离、时长、配速、轨迹质量和暂停情况 |
| 用户反馈 | 了解 RPE、疲劳、不适部位和文字描述 |
| 近期训练 | 观察连续完成、连续未完成、近 7 / 28 天训练负荷 |
| 当前阶段 | 判断用户处在适应、基础、回撤或专项阶段 |
| 历史调整 | 避免刚降负荷后立即恢复高强度 |

### 5.2 调整结果

AI 返回 `keep`、`adjust` 或 `need_more_info`。`adjust` 需要同时返回调整范围、调整课次、调整前后内容、原因、复核课次和后续观察条件。调整通常覆盖后续 1–3 节课；如果用户完成过渡课并且反馈稳定，AI 再评估后续课程是否恢复原有训练强度。

### 5.3 用户确认

训练总结页展示 AI 判断和调整前后对比。用户点击“采纳调整”后，后端写入新计划版本；用户选择保持原计划时，当前计划继续执行，同时保存本次 AI 判断结果。安全风险提示优先展示，相关课次按安全结果处理。

### 5.4 处理时效

计划初次生成使用异步任务，前端展示“智程正在生成训练计划”的加载状态并轮询任务结果。训练反馈后的调整使用结构化上下文和单次 AI 请求，返回结果后进入总结页，避免用户长时间等待。模型超时、返回格式错误或安全校验失败时，当前计划保持不变，并给出可理解的重试提示。

## 6. 训练记录与 GPS

浏览器端优先使用 `navigator.geolocation.watchPosition` 采集真实定位。训练记录包括开始结束时间、距离、用时、平均配速、暂停次数和轨迹点。只有用户在 GPS 页面点击“记录数据”后，本次跑步结果才算完成并进入后续流程。

定位失败时页面显示明确原因，不生成虚假的正式训练记录。开发测试可以使用独立测试夹具，不进入用户业务流程。

### 6.1 GPS 数据质量

前端过滤定位精度过低、速度异常和无效坐标，并保存有效轨迹点。GPS 无数据时可以结束记录，但记录会标记数据缺失，AI 会把它作为判断上下文，不把缺失数据当成真实跑量。

### 6.2 训练完成状态

用户点击 GPS 页面“结束训练”后选择“记录数据”，前端把本次跑步记录提交服务端。服务端保存成功后，今日训练页才把主体跑步标记为已记录。用户点击“完成当日训练”时，系统检查主体跑步记录和热身 / 拉伸完成状态；未完成主体跑步时提示先完成跑步。

## 7. 数据与接口

用户档案、训练计划、计划周、计划课次、训练记录、GPS 轨迹、训练反馈、AI 总结和计划调整均由后端 API 写入 MySQL。前端 localStorage 只保存登录态和页面缓存，不能替代服务端业务数据。

主要接口：

```text
POST /api/auth/register
POST /api/auth/login
GET  /api/profile
PUT  /api/profile
POST /api/ai/plans/generate-async
GET  /api/ai/plans/tasks/:taskId
GET  /api/plans/current
POST /api/plans/confirm
POST /api/runs
POST /api/runs/:recordId/feedback
POST /api/runs/:recordId/complete
POST /api/ai/plans/adjust
POST /api/ai/plans/adjust/:adjustmentId/decision
```

### 7.1 主要数据表

| 数据表 | 作用 |
| --- | --- |
| `app_user` | 账号、密码哈希和昵称 |
| `runner_profile` | 身体数据、训练基础、目标和风险筛查 |
| `training_plan` | 用户的一次完整训练计划和当前版本 |
| `plan_week` | 周次、阶段、重点、目标跑量和强度分布 |
| `plan_session` | 每日课次、热身、主体、拉伸和状态 |
| `session_record` | 实际训练结果和完成状态 |
| `gps_track` / `gps_point` | GPS 轨迹及定位质量 |
| `training_feedback` | RPE、疲劳、不适和文字反馈 |
| `ai_summary` | AI 总结和判断依据 |
| `adjustment_log` | 调整前后内容、AI 原因和用户决策 |

### 7.2 数据一致性

每个业务请求都根据登录令牌绑定用户。后端保存训练记录、反馈和调整时校验计划课次属于当前用户；前端缓存失效时重新从服务端加载。计划版本更新使用事务，确保计划、周、课次和调整记录保持一致。

## 8. 安全、隐私与错误处理

- 风险筛查命中需要医疗确认的情况时，不生成普通训练计划；
- 训练过程中出现胸闷、头晕、剧烈疼痛等信号时，页面提示停止训练并寻求专业帮助；
- AI 只能从动作库中选择动作 ID，后端拒绝未知动作和不适配动作；
- 账号密码只保存哈希值，训练和定位数据按账号隔离；
- AI 服务不可用时保留当前计划和已保存训练数据，不生成未经校验的计划；
- 接口返回 400 表示输入问题，401 表示登录失效，409 表示安全拦截，422 表示 AI 输出校验失败，503 表示 AI 服务暂不可用。

## 10. 验收重点

- 新账号只能看到自己的档案和计划；
- AI 生成结果包含具体热身、主体训练和拉伸动作；
- 动作 ID 不存在时后端拒绝保存；
- GPS 记录能够写入训练记录和轨迹点；
- 未完成主体跑步时不能完成当日训练；
- 反馈提交后能触发 AI 评估并生成调整结果；
- 用户采纳调整后，计划页展示新版本；
- 10 个原型入口均能通过 Live Server 打开并进入对应真实路由；
- 旧的历史 / 趋势入口、独立计划调整页和演示档案入口不出现在最终页面；
- Live Server 静态访问时，前端仍能通过 3001 端口调用后端。

## 11. 演示验收路径

1. 注册新账号并完成 AI 建档；
2. 在计划确认页查看目标成绩建议，选择采用建议或保留当前目标；
3. 查看 8 周阶段全貌和当前待练课次；
4. 进入今日训练，查看具体热身动作、主体训练和练后拉伸；
5. 允许浏览器定位，完成一次 GPS 训练并记录数据；
6. 提交训练反馈，查看智程 AI 的训练总结和调整结果；
7. 采纳调整后回到计划页，确认后续课次已经更新；
8. 进入“我的”，确认账号、昵称、头像、性别和隐私说明正常显示。
