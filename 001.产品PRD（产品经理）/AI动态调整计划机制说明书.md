# 智程 AI 动态调整训练计划机制说明书

## 1. 文档目的

本文档用于明确 AI 动态调整训练计划的业务目标、判断机制、系统边界、数据要求、交互流程、安全约束与验收标准。

本文档中的约束等级定义如下：

- **必须**：上线前必须满足的强制要求。
- **应**：原则上应满足；如无法满足，需在评审中说明原因及替代方案。
- **可**：可根据版本范围、数据条件或实现成本选择性支持。

## 2. 背景与问题定义

智程不是一次性生成固定周期训练计划的工具，而是根据用户实际训练表现和身体反馈持续评估、调整后续安排的 AI 跑步教练。

静态训练计划无法充分处理以下变化：

- 用户当天状态与原计划预期不一致；
- 用户在训练后出现疲劳、疼痛或其他异常反馈；
- 用户因天气、时间或个人安排未完成训练；
- 用户经过降负荷训练后，尚不能直接恢复原训练强度；
- 用户的训练时间、目标日期或能力水平发生持续变化；
- 调整建议未实际写入计划，导致建议内容与后续执行脱节。

因此，系统需要在每次有效训练及反馈提交后，基于“原计划—实际表现—身体反馈—近期状态—历史调整”进行综合判断，并输出可解释、可校验、可确认、可追溯的调整结果。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 每次有效训练反馈提交后，系统均能给出明确的计划判断结果。
2. 调整结果必须说明判断依据、影响范围、后续观察项和复核节点。
3. 对短期波动采用最小必要调整，避免训练计划频繁跳变。
4. 对持续疲劳、疼痛或能力偏离及时扩大调整范围，降低训练风险。
5. 用户确认调整后，系统必须生成新的计划版本，并在后续训练中使用该版本。
6. AI 输入、输出、校验结果、用户决定和计划版本均可追溯。
7. 快速调整应在可接受时间内返回；完整周期重排采用异步处理。

### 3.2 非目标

本机制不承担以下能力：

- 疾病诊断、用药建议或康复治疗方案；
- 替代医生、运动康复师或其他专业人员的判断；
- 基于单次异常数据直接推断长期能力变化；
- 在用户未确认的情况下直接覆盖当前执行计划；
- 通过补做已取消课程或突增训练量追赶原计划进度。

## 4. 术语与角色

### 4.1 关键术语

| 术语 | 定义 |
| --- | --- |
| 当前计划 | 用户当前正在执行的有效计划版本。 |
| 课次 | 计划中的单次训练安排。 |
| 快速调整 | 针对未来 1～3 节课或当前周剩余课次的同步调整。 |
| 剩余周期重排 | 对当前时间点之后的训练周期重新生成安排。 |
| 调整事件 | 一次 AI 判断、用户决策及计划变更记录的集合。 |
| 复核点 | 系统再次评估恢复状态或调整效果的指定课次。 |
| 过渡测试课 | 用于收集恢复证据、判断是否可恢复质量训练的低风险课次。 |
| RPE | 主观运动强度评分。具体量表范围须由产品和算法统一配置。 |

### 4.2 角色职责

| 角色/模块 | 主要职责 |
| --- | --- |
| AI 服务 | 基于结构化上下文判断是否调整、调整范围及训练内容。 |
| 后端服务 | 组织上下文、校验输出、执行幂等控制、保存记录并生成计划版本。 |
| 动作库 | 提供可用动作、适用条件、标准名称、说明及默认时长。 |
| 前端 | 展示处理状态、判断依据、调整差异、安全提示和用户确认入口。 |
| 用户 | 提交训练反馈，并决定接受调整或继续执行原计划。 |

## 5. 业务原则

1. **最小必要调整**：优先选择能够解决当前问题的最小调整范围。
2. **安全优先**：出现高风险信号时，安全提示和暂停推进优先于训练目标。
3. **数据最小化**：仅向 AI 提供完成当前判断所需的数据。
4. **用户确认生效**：除安全拦截外，计划调整必须经用户确认后方可生效。
5. **版本化管理**：任何生效的调整均须生成新的计划版本，不得直接修改历史版本。
6. **可解释与可追溯**：系统必须记录输入事实、输出结论、校验结果、用户决定及版本关系。
7. **不追赶历史进度**：恢复后从当前时间点衔接训练阶段，不补做已取消的高强度课程。

## 6. 端到端流程

```text
用户完成训练
      ↓
系统保存训练记录及 GPS 质量摘要
      ↓
用户提交主观反馈
      ↓
后端保存反馈并生成幂等键
      ↓
后端组装结构化 AI 上下文
      ↓
AI 输出判断、范围、原因及调整建议
      ↓
后端执行结构、安全和业务校验
      ↓
前端展示判断结果或调整差异
      ↓
用户确认接受调整或保持原计划
      ↓
系统保存用户决定
      ↓
接受调整：生成并启用新计划版本
保持原计划：继续使用当前版本
      ↓
在指定复核点再次评估
```

系统每次必须返回以下五类结果之一：

| 结果 | 适用说明 | 计划影响 |
| --- | --- | --- |
| 保持原计划 | 当前训练反应符合预期。 | 不修改计划，记录观察项与复核点。 |
| 短期调整 | 临时疲劳、轻微不适或一次未完成。 | 修改未来 1～3 节课。 |
| 本周重排 | 当前周剩余课次需重新组织，训练阶段仍可延续。 | 修改当前周未完成课次。 |
| 剩余周期重排 | 状态持续偏离原计划，局部调整无法恢复连续性。 | 异步生成剩余周期。 |
| 继续观察/补充信息 | 数据不足、缺失或相互矛盾。 | 保持当前计划，补充信息或安排过渡测试课。 |

## 7. AI 输入数据

后端必须将输入数据整理为结构化上下文，不得将全部历史数据无差别发送给模型。

### 7.1 本次原定训练

- 课次 ID、周次、课次序号；
- 当前训练阶段及本周训练重点；
- 训练类型；
- 目标距离、时长、配速及目标 RPE；
- 热身、主体训练和整理活动安排。

### 7.2 本次实际表现

- 实际距离和时长；
- 平均配速和最快配速；
- 暂停次数；
- GPS 有效点比例和平均定位精度；
- 训练是否完成。

### 7.3 用户反馈

- 完成度：完全完成、基本完成、部分完成、未完成；
- 实际 RPE；
- 身体感受：轻松、正常、疲劳、明显吃力；
- 疼痛评分和疼痛部位；
- 用户备注。

### 7.4 近期训练状态

- 近 7 天和近 28 天的训练次数、距离、时长及平均 RPE；
- 最近 6 次训练的完成情况及身体反馈；
- 近 30 天最长单次距离；
- 连续未完成或连续疲劳情况；
- 同一身体部位重复不适情况。

### 7.5 跑者档案

- 每周训练次数和基础跑量；
- 最长跑能力和轻松跑配速；
- 目标距离、目标时间和目标日期；
- 每周可训练天数和单次可用时间；
- 既往伤病、风险筛查结果和主要训练场地。

### 7.6 当前计划及后续课程

- 当前周次和训练阶段；
- 本周目标跑量；
- 是否为回撤周或周期末减量阶段；
- 后续 4～6 节未完成课次；
- 当前计划版本及适配说明。

### 7.7 最近一次调整

- 调整原因和范围；
- 用户是否接受；
- 调整后课次完成情况；
- 上次设置的复核点、预期响应及恢复条件。

## 8. 判断与调整机制

### 8.1 保持原计划

同时满足以下大部分条件，且不存在安全风险时，可判断为保持原计划：

- 实际训练量与原计划基本一致；
- 实际 RPE 与目标强度处于合理偏差范围；
- 身体感受为轻松或正常；
- 疼痛评分低，且未出现持续或加重趋势；
- 近期训练负荷未持续偏高；
- 下一节课本身为轻松跑、恢复课或休息；
- 本次偏差具有明确的偶发原因。

保持原计划时，系统仍须展示判断依据、观察信号和下一复核点。

### 8.2 短期调整

出现以下情况之一，且尚不需要扩大调整范围时，应优先采用短期调整：

- 单次训练出现明显疲劳；
- 轻微疼痛影响训练动作或完成度；
- 因天气、时间或临时状态未完成训练；
- 当前周课次衔接存在冲突；
- 下一节训练强度与当前状态不匹配。

短期调整最多影响未来 3 节课，并必须包含：

- 调整假设；
- 复核课次；
- 预期响应；
- 恢复条件；
- 继续维持低负荷的条件。

达到预设课次数量不等于自动恢复原强度。系统必须在复核点重新评估。

### 8.3 恢复状态判断

| 状态 | 判断依据 | 后续安排 |
| --- | --- | --- |
| 已恢复 | 疼痛消退，RPE 与身体感受恢复正常。 | 直接恢复当前阶段，或先安排一节过渡课。 |
| 部分恢复 | 状态改善，但仍有轻微疲劳或不适。 | 继续维持低负荷 1～2 节课。 |
| 尚未恢复 | 症状持续、加重或出现新问题。 | 本周重排或剩余周期重排。 |
| 信息不足 | 反馈缺失、GPS 异常或数据矛盾。 | 补充反馈或安排过渡测试课。 |

过渡测试课仅用于收集恢复证据，不以成绩为目标。参考结构如下：

```text
轻松跑 25 分钟
+ 4 × 20 秒渐进加速
+ 训练后重新提交 RPE、疲劳和疼痛反馈
```

### 8.4 扩大调整范围

#### 本周重排

适用情形：

- 当前周剩余课次存在安排冲突；
- 质量课需要调整日期；
- 用户本周可训练时间临时变化；
- 需要增加恢复间隔，但当前训练阶段仍然适用。

#### 剩余周期重排

适用情形：

- 同一部位连续出现不适；
- 疼痛持续或逐步加重；
- 连续多次训练未完成；
- 停训时间较长；
- 用户长期改变每周可训练时间；
- 用户修改目标日期、距离或成绩；
- 当前能力持续偏离原计划，短期调整无法恢复训练连续性。

剩余周期重排必须采用异步任务。新版本确认前，当前计划继续有效；如存在安全拦截，则相关课次不得继续推进。

## 9. AI 输出协议

AI 输出必须符合统一的结构化协议。建议结构如下：

```json
{
  "decision": "keep | adjust | replan | need_more_info",
  "scope": "none | micro | week | remaining_cycle",
  "confidence": 0.86,
  "summary": "本次判断总结",
  "reasonCodes": ["PAIN_RECOVERY"],
  "adjustmentEpisode": {
    "hypothesis": "调整假设",
    "reviewAfterSessionId": "w2s2",
    "expectedResponse": {
      "painMax": 2,
      "rpeReturnToTarget": true
    },
    "restoreCondition": "恢复条件",
    "holdCondition": "继续维持低负荷的条件"
  },
  "adjustments": [
    {
      "id": "adj_1",
      "targetSessionId": "w2s1",
      "before": {
        "type": "interval",
        "distanceKm": 6,
        "durationMin": 40
      },
      "after": {
        "type": "easy",
        "distanceKm": 4.5,
        "durationMin": 30,
        "title": "轻松恢复跑",
        "description": "全程保持能够正常说话的强度",
        "warmupExerciseIds": ["wu_walk", "wu_ankle"],
        "cooldownExerciseIds": ["cd_calf", "cd_quad"]
      },
      "reasonCode": "PAIN_RECOVERY",
      "reasonText": "右小腿仍有不适，建议降低后续训练负荷。"
    }
  ],
  "followUp": {
    "nextAction": "bridge_then_resume",
    "nextReviewAfterSessionId": "w2s2"
  },
  "safetyNotice": {
    "level": "warning",
    "message": "如疼痛持续或加重，请暂停跑步并寻求专业评估。"
  }
}
```

### 9.1 字段约束

| 字段/组合 | 约束 |
| --- | --- |
| `decision=keep` | `scope` 必须为 `none`，`adjustments` 必须为空。 |
| `scope=micro` | 最多影响未来 3 节未完成课次。 |
| `scope=week` | 仅影响当前周未完成课次。 |
| `scope=remaining_cycle` | 必须创建异步重排任务。 |
| `decision=need_more_info` | 必须说明需补充的信息或下一观察点。 |
| `confidence` | 仅用于内部辅助判断，不得作为安全策略的唯一依据。 |

## 10. 动作库约束

热身和整理活动属于训练计划的一部分，AI 必须使用动作库中的动作 ID 输出：

- AI 只能选择当前动作库中存在且处于可用状态的动作；
- 后端根据动作 ID 补齐标准名称、说明和默认时长；
- AI 可建议动作时长，但后端必须按动作库允许范围校验；
- 存在疼痛或既往伤病时，系统必须按动作适用条件过滤；
- 前端必须展示动作名称、时长和执行说明；
- 动作 ID 不存在或不适用时，本次调整不得写入计划。

## 11. 后端校验与计划写回

### 11.1 校验顺序

后端收到 AI 输出后，必须依次完成以下校验：

1. JSON 结构和必填字段完整；
2. `decision` 与 `scope` 组合合法；
3. 目标课次属于当前用户和当前计划；
4. 目标课次仍为未完成状态；
5. 训练类型、距离、时长和配速受系统能力支持；
6. 单次训练时长不超过用户可用时间；
7. 动作 ID 存在且适用于当前场景；
8. 输出不包含疾病诊断、用药或治疗建议；
9. 调整范围符合最小必要原则和安全边界；
10. 全部校验通过后，方可进入用户确认及写回流程。

任一强制校验失败时，不得写入部分结果。

### 11.2 用户接受调整

系统必须：

1. 保存 AI 输入事实、原始输出和校验结果；
2. 创建新的计划版本；
3. 复制未发生变化的课次；
4. 写入校验通过的调整内容；
5. 将新版本设置为当前执行版本；
6. 保存调整原因、用户决定及下一复核点；
7. 返回新计划版本号和受影响课次。

### 11.3 用户保持原计划

系统必须：

1. 保持当前计划版本不变；
2. 保存用户决定及 AI 判断原因；
3. 在下一次判断时读取本次决定和相关观察项。

### 11.4 版本关系示例

```text
计划 V1：初始计划
   ↓ 用户完成训练并提交反馈
调整事件 A：AI 建议降低未来三节课负荷
   ↓ 用户接受
计划 V2：三节课已调整，其余课次继承 V1
   ↓ 到达复核点
调整事件 B：AI 判断状态恢复，建议通过过渡课衔接
   ↓ 用户接受
计划 V3：从当前时间点继续推进
```

## 12. 前端交互要求

### 12.1 反馈提交

提交前应展示数据用途说明：

> 提交后，系统将使用本次训练数据、主观强度、疲劳及疼痛反馈生成训练总结，并评估是否需要调整后续计划。

按钮状态：

| 状态 | 文案/行为 |
| --- | --- |
| 默认 | “提交反馈并分析后续计划” |
| 请求中 | 展示“AI 正在分析”，并说明最长等待 30 秒。 |
| 失败 | 明确告知反馈已保存，并提供重新分析入口。 |

### 12.2 保持原计划

页面必须展示：

- 本次判断；
- 保持原计划的主要依据；
- 后续需要观察的信号；
- 下一复核点。

### 12.3 生成调整建议

页面必须展示：

- 调整原因及影响范围；
- 调整前后对比；
- 受影响课次；
- 调整后的热身、主体训练和整理活动；
- 恢复条件及下一复核点；
- 安全提示（如适用）；
- “接受调整”和“保持原计划”操作。

### 12.4 完整重排

页面必须展示：

- 扩大调整范围的原因；
- 任务状态：排队、生成中、已完成或失败；
- 新版本确认前的计划有效性说明；
- 新版本生成后的前后差异。

## 13. 性能、幂等与异常处理

### 13.1 快速调整性能

- 最近训练上下文：最多 6 次；
- 后续课次：最多 6 节；
- 历史调整：最多 3 条；
- GPS：仅使用质量摘要；
- AI 输出：建议控制在约 1,000 tokens；
- 目标响应时间：5～15 秒；
- 请求超时：30 秒。

### 13.2 完整重排

- 创建任务后立即返回任务 ID；
- 前端可查询排队、生成、完成和失败状态；
- 任务失败时不得覆盖当前计划；
- 用户离开页面后再次进入，仍可查询任务结果。

### 13.3 幂等要求

同一训练记录和同一反馈版本只能创建一个有效调整任务。重复提交时，系统应返回已有任务或待确认结果，不得生成并行重复任务。

### 13.4 异常处理

| 场景 | 用户侧结果 | 系统处理 |
| --- | --- | --- |
| AI 正常返回 | 展示判断或调整差异。 | 保存输入、输出和任务状态。 |
| AI 请求超时 | 提示稍后重试。 | 保留反馈，当前计划继续有效。 |
| AI 服务不可用 | 提示服务暂时不可用。 | 不影响已保存的训练与反馈。 |
| AI 输出格式异常 | 不展示不完整调整。 | 自动执行一次结构化修复；仍失败则保持原计划。 |
| 课次或动作不存在 | 提示暂时无法生成安全调整。 | 不写入任何计划变更。 |
| 数据不足或矛盾 | 提示补充信息或继续观察。 | 返回 `need_more_info`。 |
| 用户重复提交 | 返回已有任务状态。 | 不创建重复任务。 |

## 14. 安全与隐私要求

### 14.1 安全优先信号

出现以下任一信号时，系统必须进入安全优先流程：

- 胸痛或胸部压迫感；
- 异常呼吸困难；
- 头晕、眼前发黑或协调能力下降；
- 心悸或明显心律异常感；
- 突发剧烈关节痛；
- 疼痛持续加重；
- 其他经安全规则配置的高风险信号。

安全优先流程至少包括：

1. 暂停相关训练推进；
2. 展示明确的停止训练提示；
3. 建议用户根据实际情况寻求专业评估；
4. 禁止 AI 输出疾病诊断、用药或康复治疗方案；
5. 记录命中的安全规则及处理结果。

安全阈值及提示文案须经安全与合规评审后配置，不应仅由模型自行判断。

### 14.2 数据最小化

- 仅向 AI 发送训练判断所需字段；
- GPS 仅以质量摘要参与判断；
- 手机号、昵称等直接身份信息不得用于训练分析；
- 自由文本备注必须限制长度并进行必要的安全处理；
- 提交前必须展示 AI 数据使用说明；
- 数据保存期限、删除机制及第三方 AI 服务边界须在隐私评审中确认。

## 15. 验收标准

### AC-01 正常训练

- 正常完成训练、RPE 符合预期且无明显不适时，系统返回保持原计划；
- 页面展示判断依据、观察项和下一复核点；
- 当前计划版本不发生变化。

### AC-02 短期疲劳或轻微不适

- 系统可识别短期降负荷需求；
- 调整范围不超过未来 3 节未完成课次；
- 已完成课次不发生变化；
- 调整后的距离、时长、训练内容和动作可在前端完整展示。

### AC-03 用户确认

- 用户接受后生成新计划版本，前端展示新内容；
- 用户保持原计划后，训练内容不发生变化；
- 两类决定均写入数据库并可追溯。

### AC-04 调整后复核

- 系统结合疼痛、RPE、疲劳和训练表现判断恢复状态；
- 完成降负荷训练不会自动恢复高强度训练；
- 信息不足时可请求补充反馈或安排过渡测试课；
- 恢复后从当前时间点衔接，不补做已取消课程。

### AC-05 周期重排

- 持续性问题可触发本周或剩余周期重排；
- 剩余周期重排以异步任务执行；
- 新版本确认前，当前计划仍可查询；
- 重排失败时不得影响当前计划。

### AC-06 性能与幂等

- 快速调整目标响应时间为 5～15 秒；
- 30 秒超时后返回明确状态；
- 同一训练记录和反馈版本不会创建多个有效任务。

### AC-07 数据准确性

- 训练与反馈数据准确写入数据库；
- AI 使用真实训练数据和反馈；
- 调整确认后，前端展示数据库中的当前计划版本；
- 动作名称、时长和说明均来自动作库。

### AC-08 安全拦截

- 命中高风险信号后，系统暂停相关训练推进；
- 页面展示经评审的安全提示；
- AI 不输出诊断、用药或治疗建议；
- 安全规则命中及处理结果可追溯。

## 16. 典型场景

### 场景 A：状态正常，保持原计划

用户完成轻松跑，实际 RPE 与目标相符，无疼痛，身体感受正常；下一节为轻松跑。系统返回 `keep + none`，并设置下一复核点。

### 场景 B：单次疲劳，短期调整

用户在质量训练后反馈明显疲劳，并出现非高风险的不适。系统返回 `adjust + micro`，降低后续课次负荷并设置复核点。若疼痛达到安全规则阈值，则优先进入安全流程。

### 场景 C：降负荷后恢复

用户完成降负荷课次后，疼痛逐步消退，RPE 回到目标范围。系统判断为已恢复，可先安排过渡课，再衔接当前训练阶段。

### 场景 D：降负荷后仍不适

用户完成降负荷课次后，同一部位不适仍持续，疲劳未改善。系统扩大调整范围，按规则进入本周重排、剩余周期重排或安全优先流程。

### 场景 E：GPS 数据异常

GPS 有效点不足，但训练时长、RPE 和身体感受可信。系统降低 GPS 数据权重，返回保持原计划或继续观察，不因单次定位异常直接重排训练周期。

## 17. 分阶段落地建议

5. 完成调整差异展示、用户确认和计划版本写回；
6. 增加训练前状态确认及安全规则配置；
7. 完成本周重排和剩余周期异步重排；
