# 智程后端 API

## 产品 AI 定位（Demo 当前范围）

智程当前 Demo 只支持普通业余跑者的 10 公里、8 周训练目标。

产品的两个核心 AI 功能是：

1. 根据跑者档案和专业训练模板，生成真正个性化的每日训练计划；
2. 根据实际训练数据和用户反馈，动态调整后续训练计划。

模板库只提供训练阶段、训练重点和质量课结构。AI 负责结合跑者档案生成每日距离、时长、配速、训练结构和个性化原因；后端负责安全校验、边界校验和最终保存。

登录与注册服务，使用 Node.js、Express 和 MySQL。账号对应数据库 `app_user.phone`，密码使用 Node.js `scrypt` 加盐哈希保存。

## 启动

```powershell
cd 003.前端代码/backend
Copy-Item .env.example .env
# 在 .env 中填写 Docker MySQL 密码
npm install
node src/seed.js       # 首次启动时创建演示账号 123 / 123456
npm run dev             # http://localhost:3001
```

前端开发服务 `http://localhost:5173` 已配置 `/api` 代理到 `http://localhost:3001`。如果前端不是通过 Vite 开发服务访问，可设置 `VITE_API_BASE_URL=http://localhost:3001/api`。

## 接口

- `GET /api/health`：检查 API 与 MySQL
- `POST /api/auth/register`：注册，参数 `{ phone, password, nickname? }`
- `POST /api/auth/login`：登录，参数 `{ phone, password }`
- `GET /api/auth/me`：使用 `Authorization: Bearer <token>` 获取当前账号
- `DELETE /api/auth/account`：注销当前账号，并级联删除账号关联数据
- `GET /api/profile`：获取当前用户跑者档案
- `PUT /api/profile`：保存或覆盖当前用户跑者档案
- `POST /api/profile/confirm`：确认当前用户跑者档案

| `T10-ADAPT-3` | 10 公里适应型 · 常规起步 | 3 次 | 需要先建立稳定训练连续性 |
| `T10-ADAPT-4` | 10 公里适应型 · 规律重建 | 3 次 | 已有一定规律，但暂时没有 10 公里成绩 |

## 每套模板的具体内容

模板中的质量课类型含义：

- `aerobic`：有氧跑，负责建立基础和恢复；
- `tempo`：节奏跑，负责提升持续跑能力；
- `interval`：间歇跑，负责提升速度储备；
- `race`：目标配速跑，负责建立 10 公里专项节奏。

同一分类下的三套模板共享训练阶段骨架，但训练频率、最低周跑量和递进速度不同。这是为了避免为每个小档位重复维护一套完全不同的训练逻辑。

## 模板分类依据

### 第一层：安全筛查

先判断是否允许生成计划：

```text
需要医疗确认 → 不生成正常训练计划
档案关键字段缺失 → 不生成正常训练计划
风险筛查通过或可训练 → 进入模板匹配
```

### 第二层：训练基础

以下数值是**产品 Demo 规则**，不是国家标准：

```text
适应型条件：
  周跑步次数 ≤ 2 次
  或近 3 个月周跑量 < 15 公里
  或最长连续跑 < 6 公里
  或没有 10 公里最好成绩

进阶型条件：
  有 10 公里最好成绩
  且周跑步次数 ≥ 3 次
  且周跑量 ≥ 22 公里
  且最长连续跑 ≥ 8 公里
```

不满足适应型条件、又不满足进阶型条件的跑者进入基础提升型。

### 产品 Demo 阈值的推导过程

这些数字不是从某一篇资料中直接抄来的，而是把权威资料中的“训练习惯、近期负荷、个体化和循序渐进”转成系统可以执行的判断条件。推导步骤如下：

#### 1. 先确定判断维度

从建档字段中选出会直接影响训练承受能力的 4 个指标：

| 指标 | 为什么使用 |
| --- | --- |
| 每周跑步次数 | 判断是否形成稳定训练频率 |
| 近 3 个月周跑量 | 判断近期累计负荷，而不是只看一次最好成绩 |
| 最近最长连续跑 | 判断连续运动和长距离训练基础 |
| 10 公里最好成绩 | 判断是否有可用于专项配速的实测依据 |

每周可训练天数另外用于选择同一类别中的低频或高频版本。

#### 2. 先设“适应不足”边界

目标距离是 10 公里，因此把以下情况视为尚未形成 10 公里训练基础：

- `最长连续跑 < 6 公里`：尚未完成目标距离的约 60%，长距离能力不足；
- `周跑量 < 15 公里`：即使每周跑 3 次，平均每次也只有约 5 公里，累计负荷仍偏低；
- `每周跑步次数 ≤ 2 次`：训练频率不足以支撑常规质量课安排；
- `没有 10 公里成绩`：缺少专项配速的实测锚点。

这里采用“任一项命中即进入适应型”，是因为任何一个明显短板都可能使质量课风险上升。适应型先安排有氧跑，再逐步加入短节奏跑。

#### 3. 再设“具备专项基础”边界

进阶型要求所有条件同时满足：

- `每周跑步次数 ≥ 3 次`：具备稳定频率；
- `周跑量 ≥ 22 公里`：约为目标距离的 2.2 倍，说明已有持续累计负荷；
- `最长连续跑 ≥ 8 公里`：接近 10 公里目标，具备较好的连续跑基础；
- `有 10 公里成绩`：可以用实测成绩计算专项配速。

采用“全部满足才进入进阶型”，是为了避免只凭一次 PB 或单项跑量就安排间歇训练。任一项不足，就先进入基础提升型。

#### 4. 设置进阶高档边界

进阶型内部再用更高条件区分 4 次训练版本：

- `每周跑步次数 ≥ 4 次`；
- `周跑量 ≥ 30 公里`，约为目标距离的 3 倍；
- `最长连续跑 ≥ 10 公里`，已经完成目标距离级别的连续跑。

三个条件同时满足时，才使用 `T10-ADV-4`。否则使用 3 次训练版本，避免把训练时间和负荷不足的跑者强行放入高频计划。

#### 5. 最终分类算法

```text
风险需要医疗确认
→ 阻止生成正常计划

否则，只要以下任一条件成立：
  每周跑步次数 ≤ 2
  周跑量 < 15 公里
  最长连续跑 < 6 公里
  没有 10 公里成绩
→ 适应型

否则，如果以下条件全部成立：
  每周跑步次数 ≥ 3
  周跑量 ≥ 22 公里
  最长连续跑 ≥ 8 公里
  有 10 公里成绩
→ 进阶型

否则
→ 基础提升型
```

因此，`15/22/30 公里`、`6/8/10 公里`和`2/3/4 次`不是官方分级，而是根据目标距离、训练频率、近期负荷和连续跑能力建立的保守执行界限。它们可以随着真实用户的完成率、RPE、疲劳和疼痛数据重新校准。

### 第三层：同类模板细分

- 可训练天数不足或最近跑步次数不超过 2 次：适应型低频起步；
- 训练次数达到 3 次，但基础较低：适应型常规起步；
- 没有 10 公里成绩，但已经有较规律训练：适应型规律重建；
- 基础提升型按照每周 3 次、每周 4 次和较高周跑量进行细分；
- 进阶提升型按照 3 次基础、4 次高频和 3 次高周量进行细分。

这些阈值的作用是让 Demo 能稳定选择模板，并不代表某个跑者只能使用某一套模板。实际计划还会继续受到伤病、疲劳、RPE、实际完成度、训练场地和单次最大时长的约束。

8 周结构：

```text
第1周：适应期 · 有氧基线
第2周：专项提升 · 持续节奏
第3周：回撤周 · 恢复有氧
第4周：专项提升 · 分段间歇
第5周：专项提升 · 分段间歇巩固
第6周：回撤周 · 短节奏维持
第7周：专项提升 · 10 公里专项节奏
第8周：周期收尾减量 · 专项唤醒
```

## AI 如何生成训练计划

### 1. 获取跑者档案

后端接收以下字段：

- 最近每周跑步次数
- 近 3 个月平均每周跑量
- 最近最长连续跑距离
- 10 公里最好成绩
- 平时舒服慢跑配速
- 每周可训练天数
- 单次最大训练时长
- 伤病情况
- 风险筛查结果
- 10 公里目标用时

### 2. 执行安全闸门

如果风险筛查需要医疗确认，系统会暂停正常训练计划生成；出现胸痛、胸闷、头晕、心悸、异常呼吸困难或明显疼痛时，系统会优先进入安全处理流程。

### 3. AI 结合模板生成计划

模板只提供每周蓝图，不直接写死每日距离、时长和配速。后端模板负责：

- 阶段顺序
- 质量课类型
- 回撤周
- 周期收尾减量
- 每周训练重点

AI 需要结合跑者档案生成：

- 每日训练距离
- 单次训练时长
- 轻松跑和质量课配速
- 长距离上限
- 单次最大训练时长
- 热身、放松和力量训练内容

后端只负责检查 AI 输出是否满足安全边界和页面所需字段。

### 4. AI 的两项核心职责

第一项是初始计划生成：AI 读取跑者档案和模板库，生成 8 周的每日训练内容、个性化原因和注意事项。

第二项是动态调整：AI 读取原定训练、实际距离、实际时长、实际配速、完成度、RPE、疲劳、疼痛、备注和历史记录，生成结构化的后续调整建议。

AI 的安全边界包括：

- 绕过风险筛查
- 超过单次最大训练时长
- 明显超过近期最长跑距离
- 在恢复不足时盲目增加训练量
- 做医学诊断
- 承诺用户一定达到目标成绩

### 匹配训练模板

```http
POST /api/plans/match-template
Authorization: Bearer <token>
Content-Type: application/json
```

请求体：

```json
{
  "profile": {
    "targetDistance": "10K",
    "runsPerWeek": 3,
    "weeklyKm": 20,
    "longestRunKm": 8,
    "best10kPace": 390,
    "availableDays": 3,
    "riskLevel": "low"
  }
}
```

返回结果包含匹配到的模板、8 周 `blueprint` 和 `ruleType: "产品 Demo 规则"`。

### AI 计划生成与动态调整接口（下一阶段）

计划生成建议使用：

```http
POST /api/ai/plans/generate
```

动态调整建议使用：

```http
POST /api/ai/plans/adjust
```

两类接口都应由后端调用大模型。前端不直接持有模型密钥。大模型返回结构化 JSON，后端先校验 10 公里、8 周、训练时长、长距离上限、周跑量递进、伤病和风险闸门，再保存到数据库。

如果模型输出不符合安全边界，后端应先尝试自动修正；仍不合格时拒绝保存并返回明确错误，而不是把模型原文直接展示给用户。

## 周期收尾减量说明

“周期收尾减量”是产品规则：降低总训练量，保留少量训练刺激，不安排新的高强度挑战，也不通过补课追赶未完成训练，为下一周期评估保留恢复空间。

## 依据与边界

AI 接口输入、输出、状态、错误处理和校验规则详见：[AI接口契约.md](./AI接口契约.md)。

模板设计参考国家体育总局《全民健身指南》和《运动处方中国专家共识（2023）》中的个性化、循序渐进、FITT-VP、恢复、热身放松和运动安全原则。

具体周跑量、频率、最长跑和模板分层阈值是本产品的 Demo 设计规则，不应表述为国家标准。详细证据链见：

`frontend/docs/10k-template-library.md`
